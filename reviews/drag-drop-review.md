## Summary
Solid, well-structured drag-and-drop game with a few correctness bugs, one memory leak, and a minor UX issue worth fixing before ship.

## Issues

- **[severity: high]** Correctness — `cleanupDrag()` is called before the hit-test on `pointerup` (lines 262, 466). `cleanupDrag()` sets `dragging = false` and nulls `clone`. The guard at the top of the handler (`if (!dragging || !clone) return`) would pass, but the issue is that `cleanupDrag()` runs unconditionally even when the word is already `dd-item-done`. In that case the early-return fires at the top of `pointerdown` so `clone` is never set — meaning `cleanupDrag()` in `pointerup` is a no-op. This is technically safe today, but the guard `if (!dragging || !clone) return` is checked *before* `cleanupDrag()`, so if a second pointer event races in while `dragging = true` (e.g. multi-touch), the second `pointerup` will call `cleanupDrag()` and set `dragging = false`, then fall through to the hit-test using `e` from the second pointer but `itemId`/`item` from the second word element's closure — which is correct. The real bug: `cleanupDrag()` is called *before* reading `e.clientX/e.clientY` for the hit-test. The clone is removed and `dragging` is cleared before the match logic runs, so if the match is correct and triggers `showFact` → `factDismissCallback` → a new drag could technically start while the fact modal is open. This is a latent race, not a crash, but should be fixed: move `cleanupDrag()` to *after* the hit-test, or at minimum after the coordinates are captured.

- **[severity: high]** Correctness — In `showCompletion` (line 549), the overlay is appended to `container.querySelector('.dd-canvas-panel')`. For Mode B (`word-to-position`), the canvas panel contains the diagram container which contains the fact modal. But `container` here is the `dd-game` screen element — `.dd-canvas-panel` exists in both modes, so the selector works. However, the `transitionTo` calls inside the overlay's button handlers pass `container` (the original `dd-game` screen) as `oldEl`. By the time the user clicks "Play Again" or "Next Level", this screen may have already been removed from the DOM by a prior `transitionTo` call (e.g. if the user somehow triggers two completions). The `transitionTo` function has a guard `if (!parent) return` — but this means the new screen is never inserted and the game silently breaks. This is unlikely in normal play but worth noting.

- **[severity: medium]** Memory leak — The typing animation in `createIntroScreen` stores its timer in `typingTimer` and cancels it on level-card click. However, if the user hits the home button (line 101) instead of selecting a level, `typingTimer` is never cleared. The timer will keep firing against a detached DOM node. The `el.parentNode` check inside `typeChar` will eventually stop it (once the screen is removed), but there's a window where the timer fires against a detached element. The same pattern exists in both gameplay screens (`typeInstr` at lines 192–198 and 395–401) — these timers are never stored, so they can never be cancelled. If the user taps "Home" mid-animation, the timer fires against a detached node. The `el.parentNode` guard stops new characters from appending but the `setTimeout` chain keeps re-queuing until the check fires. Storing and clearing these timers on navigation is the clean fix.

- **[severity: medium]** Correctness — Level 6 (`indigenous-farming`) has 6 items, but `LEVEL_ICONS` only has 6 entries (indices 0–5) — that aligns correctly. However, `level.items.length` for level 6 is 6, while levels 1, 2, 3, 4, 5 have 5, 5, 5, 4, 5 items respectively. The completion check `matchedSet.size === level.items.length` is correct. No bug here — just confirming the asymmetry is intentional.

- **[severity: medium]** UX / Correctness — When a correct match is made for a non-final item, `showFact(item)` is called with no `onDismiss` callback (lines 303–305, 507). The fact modal opens. While the modal is open, `dragging` is `false` (cleaned up before the match), so a user can start dragging another word immediately — before dismissing the fact. The next drag will work fine mechanically, but the fact modal remains visible and covers the drop targets in Mode A (it sits inside `.dd-canvas-panel`). In Mode B the modal is inside `.dd-diagram-container`, covering the diagram. A user dragging while the modal is open cannot see or hit the targets. Consider either: blocking new drags while the fact modal is visible, or auto-dismissing intermediate facts after a short delay.

- **[severity: medium]** Correctness — `transitionTo` appends `newEl` to `parent` and starts an `animationend` removal of `oldEl`, with a 400ms fallback `setTimeout` in case `animationend` never fires. But `transitionTo` is also called from inside the completion overlay's button handlers, where `container` is the `dd-game` screen. At that point the overlay is a child of the screen — appending the new screen to the same parent as the old one is correct. The issue: the `animationend` listener on `oldEl` calls `oldEl.remove()`, and the 400ms timer also calls `oldEl.remove()`. Both will fire (the `{once: true}` flag prevents the listener double-fire, but the timer always fires). Double-removing a node is harmless in the DOM, so this is low risk — but the timer is unnecessary given the `{once: true}` listener.

- **[severity: low]** Readability — `createWordToImageScreen` and `createWordToPositionScreen` share ~100 lines of near-identical code: the word sidebar, drag clone logic, `showFact`, `factDismissCallback`, `showHint`, `resetInstruction`, the typing animation, and the home button. This duplication means any bug fix or UX change needs to be applied in two places (as already seen with the identical timer leak). Extracting a shared `setupDragSidebar(el, level, levelIdx, getDropTarget)` helper would reduce duplication significantly.

- **[severity: low]** Error handling — `level.items.find(i => i.id === itemId)` on lines 265 and 469 can return `undefined` if a `data-item-id` attribute is stale or mismatched with content data. Accessing `item.label` or `item.fact` on `undefined` would throw. This can't happen with the current static content, but a defensive check (`if (!item) return`) costs nothing.

## Verdict
NEEDS CHANGES — the `cleanupDrag`-before-hit-test ordering issue and the dragging-while-modal-is-open UX gap are the most important fixes. The timer leak in the gameplay screens should also be addressed before shipping to a kiosk where the game may run for hours.
